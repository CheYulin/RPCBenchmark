# Finite SDK RPC diagnostic: observer gate failed

This optional diagnostic uses the real DataSystem SDK and Worker. It changes neither product code nor the default RPCBenchmark build. It follows the rejected server idle-timer experiment. Its purpose is to validate a bounded capture tool and locate latency stages, while retaining the failed measurements and the unmet RPC P99 target.

The SDK is the buffered singleflight checkpoint `7f7e7e34be66eb97bbca4a8643f8c9f1fa589f78` (SDK SHA256 `74112f13e18ca727216d1f87b06b98b5e775932d9dcdc5c7c44d03af056308c3`), with the unchanged Worker SHA256 `98671d3762965dcc69b8a3cae74d8a0b82f3e8fcd3dec5e2a0d1103dc478e3fa`. This is a measurement SDK with the existing ABI2 capture provider. A production SDK without that provider cannot run enabled capture. Original bRPC defaults and the four server IO workers remain unchanged.

## Workload and interpretation

There are 32 persistent caller threads and 64 keys, with 4 KiB values. Each caller makes 8,192 warmup calls and 49,152 measured calls, issuing its next API only after the previous one returns. Get and Set each run off/on/on/off using the same executable, SDK, Worker, eight SDK physical cores, eight different Worker physical cores, and nice 10. Actual duration and QPS vary. This is a finite closed loop, with concurrency tapering as callers finish; it is not the earlier fixed-duration capacity workload or fixed offered-load acceptance. Each formal window has 1,572,864 measured calls. A separate smoke executable first completes Get/Set with capture off and on, using 8/16 calls per caller.

Every Get verifies all 4 KiB; every Set checks status. Set uses distinct seed, warmup and measurement values. Final reads check both written and untouched keys after capture disarm. This verifies final writes, not each individual overwrite. All API attempts, errors, byte mismatches and histogram counts remain explicit. Latencies have one-microsecond upper-bound bins through 8,192 microseconds and power-of-two upper bounds thereafter.

IDs are `ordinal * 32 + caller`, unique within each phase. The unchanged helper in `../ds-latency30/` selects IDs with seed 17/modulus 512: 527 warmup and 3,065 measured APIs. The driver independently records all preselected APIs and errors into preallocated caller-owned ledgers. The decoder checks the complete selected set, actual Linux TIDs, timestamps, RPC ordinals, method counts, final seal and cumulative prefixes. Optional server metadata does not filter the main RPC population. Full API counts and sampled RPC counts have separate denominators. About 31 sampled points lie in each window's upper one percent; sampled RPC quantiles are diagnostic empirical estimates.

API service time includes capture Begin and ends when the SDK returns. Validation and End are excluded from that span; a separate observer-inclusive histogram includes both. QPS includes all work between the first API begin and last caller completion. CPU uses SDK plus Worker process ticks bracketing each complete phase, including barriers and background work, excluding between-phase dumps, final readback and shutdown. It is not pure RPC CPU. Caller first/last finish timestamps disclose taper.

The RPC boundary wraps the generated synchronous channel call. For coro_rpc it includes request/response adaptation and serialization, not just socket IO. Server processing/execution timestamps come from the generated service adapter, after initial dispatch and protobuf parsing and before final response encoding/IO. `RPC − server_processing` is computed per call before quantiles. It is a mixed residual containing scheduling, adaptation, IO and network, not pure network time.

## Reproduction and safety checks

Use `python3 build_local.py --sdk-dso <measurement-SDK> --sdk-include <SDK-include-directory> --output <new-build-directory>`. Additional dependency paths can be supplied with repeated `--library-dir`. The public helper reuses the existing ABI2 helper sources; output must be new. The original remote build used GNU 15 and the same `-std=c++20 -O2 -pthread -Wall -Wextra -Werror -fPIC -pie` flags. The portable public build wrapper itself has only command/input validation evidence; the retained private build commands and binaries supplied the executed SDK tests.

PIC matters: an initial non-PIC executable resolved the SDK function anchor to its own PLT. The enabled smoke rejected that identity before GO. A minimal `anchor_probe.cpp` reproduced non-PIC failure and PIC/PIE success against the same SDK. Strict same-image checks were retained. Original binaries and failure evidence were archived, not treated as valid performance windows.

Run `python3 -m unittest discover -s . -p 'test_*.py'` for the 73 analysis, file-contract and calibration checks. `plan_test.cpp` provides seven C++ finite-ID, selector, capacity and histogram checks; compile it in GNU C++20 without `NDEBUG`. The analysis tests retain missing-module and malformed-boundary RED failures; file tests reproduced three false-pass bugs before correction. The SDK smoke and eight formal windows then passed independent identity, byte, count, prefix and cleanup checks. This is not sanitizer/OOM/TLS qualification for this driver or a complete production test suite.

Before using the driver, create a fresh case directory and log directory, set `DS_BENCH_WORKER_HOST`, `DS_BENCH_WORKER_PID`, `DS_BENCH_RPC_CAPTURE_MODE=off|enabled`, `DS_BENCH_RPC_CAPTURE_SDK` to the exact loaded DSO, seed 17 and modulus 512. The recorded windows set `DATASYSTEM_RPC_BACKEND=coro_rpc`, `DATASYSTEM_CORO_RPC_PORT=<separate-coro-port>`, and `DATASYSTEM_CORO_CALLER_IO=1`. `DS_BENCH_ROUTED` was absent, preserving the original SDK driver default `enableLocalCache=true`; isolated remote routes and capture method counts separately verify actual RPC use. Invoke `closed-loop-sdk get|set <worker-port> <log-directory> <new-case>/driver`. It writes READY with 32 TIDs and waits for `GO` on stdin before capture Arm. The controller must verify actual executable/DSO mappings, source hashes, PID start time, routes, affinity and niceness before releasing it. The experiment used isolated parent/client network namespaces and a private veth; the repository does not install a new always-on service.

One thread owns each slot and ledger. Main arms only after all owners register, snapshots only while all callers are quiescent, seals before releasing unregister, then joins callers. Readback and SDK shutdown precede capture Close and buffer destruction. Fatal contract failures retain a partial prefix and terminate rather than freeing lent arrays while users remain active. The controller cleans only positively identified owned sessions. Capture arrays plus the helper reserve stay below 128 MiB; independently bounded histograms and ledgers add memory. This is not a 128 MiB total-RSS or continuous peak-memory claim.

## Results retained

All four smoke cases and eight formal windows passed data-quality checks, including **12,582,912 successful measured APIs**, no API errors or Get byte mismatches, complete selected ledgers, source post-checks and owned-session cleanup. The full archive contains 1,179 regular files, individually SHA-verified, at archive SHA256 `cf4aaceaf1ff6c7e7696b37763bdd60c8d9444cdc33d9c8e08740f229e4622e0`. It also preserves the initial setup and qualification failures. Formal performance windows were not retried.

The predeclared observer gate failed. Get off P99 was 1,051/754 microseconds, on 807/810; control drift was 28.26%, and the reverse directional pair regressed 7.43%. Set off P99 was 1,501/1,482, on 1,641/1,496; the first pair regressed 9.33%, CPU/success increased 3.54%, and QPS decreased 4.15%. Positive medians cannot waive individual pairs or drift. No BPF follow-up was entered under that plan.

Uncalibrated sampled observations show Get server execution P99 about 15 microseconds versus RPC sample P99 799–1,005 microseconds; per-call mixed residual P99 was 786–987 microseconds. Set execution P99 was 441–465 microseconds, with mixed residual P99 1,260–1,491 microseconds. These identify a diagnostic direction outside the measured business span; they do not establish causality or a reliable overhead budget. `result.json` retains all windows, denominators, failures and limitations. Numeric fractions are rounded to six decimals; full precision remains in the archive.

There is no bRPC counterpart in this matrix. RPC P99 reduction of 30%, scheduled-arrival SDK E2E, mixed/peak/fault-memory behavior and full default/OFF build/CI gates remain unachieved or unverified. No new optimization is promoted into DataSystem.
