# Native server idle monitor experiment (rejected)

This optional experiment keeps a five-second server idle timeout in both performance arms. The client is the same buffered singleflight executable in all eight windows. It changes only server timer scheduling: the candidate refreshes a deadline while retaining one outstanding timer, then cancels that wait on close. It does not change the default RPCBenchmark build or DataSystem.

The pinned upstream is yalantinglibs `45c6463c0afbcc46262e373effa30635be3846a0`. `apply_idle.py --upstream-include <include> --output <new-directory>` validates both upstream server headers before creating output. Overlay the two generated headers into a separate include tree. The previously published buffered singleflight client header remains fixed. The original timer policy is the constructor default; the candidate is an immutable typed constructor option.

The connection IO executor owns the deadline, active and pending flags. The timer callback holds the connection until completion. Close cancels the timer so closed connections cannot accumulate self-held references for another five seconds. While a handler is running, idle expiry does not close the connection; the last response starts the new idle period. There are no new threads, locks, per-request timer allocations in the candidate, wire changes, retries or durable state. Rollback is to omit the explicit candidate policy. Other transports, OOM and production lifecycle bounds remain unqualified.

## Correctness and reproduction

Compile `idle_timer_test.cpp` using GNU C++20 and `-DCORO_RPC_IDLE_TIMER_TEST`, the isolated include tree, `-include cstdint -include algorithm -pthread`, and system include paths for `ylt/thirdparty` and `ylt/standalone`. The seams and wait counter are excluded from release performance builds. Nine cases passed in release and ASan/UBSan with leak checking; descriptors returned to baseline. The original header produced the expected missing-interface compile failure. A mutation that omitted cancellation on close failed the expected weak-reference release assertion. The cases include repeated refresh, default per-request scheduling, long and overlapping handlers, close without resurrection, timeout zero, connection churn and expiry against a refreshed deadline.

Compile `rpc_lifecycle_test.cpp` without test seams and run it with an unused port in an isolated loopback network namespace. Both policies passed actual RPC echo bytes, a handler longer than the 40 ms test idle interval, idle disconnect, reconnect and server stop (four policy/workflow checks). These are native checks, not DataSystem correctness qualification.

`server.cpp` links with the unchanged `lab.cpp` and `lab.h` from the repository `src/` directory, and requires `--idle-coalesced 0|1`; both choices use five seconds. The client executable and sources come from the published buffered singleflight experiment, always `--singleflight 1`. Use four server IO workers, 4 KiB echo, one-second warmup and three-second measure. Run original/candidate/candidate/original at concurrency 1, then 32. Client and server each use four distinct physical cores, nice 10 and SCHED_OTHER. A separate metadata core, private network namespace and per-role cgroups collect resource and cleanup evidence. The eight frozen windows were not retried.

## Result and limits

At concurrency 32, original P99 was 177 and 159 microseconds; candidate P99 was 158 and 177. One directional comparison improved, the other regressed 11.3%; arm medians were essentially unchanged. Throughput median increased 0.75%, CPU per success decreased 1.34%. Original P99 drift was 10.17%, failing the frozen 3% drift gate. The incremental screen also required at least 5% conservative P99 improvement in both directional comparisons and the median, with throughput and CPU within 3% at both concurrencies. It failed.

At concurrency 1, candidate P99 was 35/36 versus 40/39 microseconds; throughput median increased 2.49% and CPU per success decreased 4.10%. Those results cannot waive the concurrency-32 failure. CPU covers client setup, warmup, measurement and drain plus server waiting, divided by all successful warmup and measured calls; it is not pure RPC CPU. Latency includes calls started before the cutoff and completed afterward. The shared host was not exclusive, and the observer was not calibrated.

All eight windows passed byte, success/cohort, source, connection and resource checks. Both owned role cgroups were empty afterward. `result.json` retains all windows, failures, predeclared gates and archive identity; displayed fractions are rounded to six decimals while the retained archive has full precision. This experiment does not establish the cause of DataSystem Get/Set tail regression and is not promoted into DataSystem. RPC P99 reduction of 30% remains unachieved.
